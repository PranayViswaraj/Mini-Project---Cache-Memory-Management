# 03 — Experiment Results and Analysis (Phase 1 baseline + Phase 2 adaptive)

All numbers below are **measured on the RTL** (Verilator build of the same Verilog that passed the regression)
and **every one of the 488 runs was also reproduced exactly by the independent Python reference model**
(350 baseline + 138 ablation; counters, stall cycles, switch and window counts). Tables are generated by
`sim/make_report.py` from `results/*.csv`; nothing is typed in by hand.

## 1. Method (fair-comparison rules)
* Identical RTL, cache geometry, trace, memory latency, initial (cold) state and counters for every row group;
  **only `cfg_policy` changes**.
* Memory latency `LAT = 10` cycles/word → read-miss penalty `1 + 8·10 = 81` cycles beyond the 1-cycle hit.
* Metrics: hit rate, **stall cycles** (counted by the hardware), execution cycles = accesses + stalls,
  **measured AMAT = execution cycles / accesses**. Write-through means every write also stalls `1 + LAT`; this cost is identical for all policies.
* Workloads (24 k–25 k requests each, deterministic): `seq`, `rand`, `stride`, `conflict`, `loop`, `scanhot`, `matmul`, `fir`, `image`, `phase`.
  `conflict`, `scanhot` and `phase` are **deliberately policy-sensitive** (they are adversarial to LRU); the others are not. This is a design choice of the study and must be stated whenever results are quoted.
* Geometries: 1/2/4/8/16 KB × 2-way (Random, LRU, Adaptive) and 4-way (Random, LRU, **PLRU**, Adaptive).
* Adaptive defaults: `WIN=2048, SAMPLE_N=64, MARGIN=4, CONF_THRESH=2, MIN_HOLD=1`; it starts as LRU.

## 2. Does the replacement policy matter on these workloads?
Yes — but only on some of them.
* In **53 of the 100** (geometry, workload) cases the best and worst fixed policy differ by more than 5 % in stall cycles.
* Among those 53 cases the best fixed policy was **Random in 38 and LRU in 15**; PLRU was never the unique best. **No single fixed policy wins everywhere.**
* `rand` is insensitive (max spread 1.1 %); `conflict` is extremely sensitive (up to 148.5 % spread; LRU gets **0 % hits** at 4 KB for both 2-way and 4-way, Random gets 33.1 % / 59.8 %).
* `loop` favours LRU (e.g. 4 KB 4-way: LRU 274 509 vs Random 419 013 stall cycles).
* **PLRU vs true LRU (4-way):** the two differ in 21 of 50 cases; among those PLRU is on average only 1.2 % different (range −19.0 % … +9.6 %), i.e. PLRU is usually a good approximation but not always. This justifies evaluating PLRU only at 4-way.
* Caveat: Random's frequent wins reflect that these synthetic workloads include cyclic/scan patterns pathological for LRU; real programs may favour LRU more.

## 4. Does the adaptive controller help? (answer from the data)
**Honest summary: sometimes, and not as much as the best fixed policy.**
* Versus **LRU** (its starting policy): better by >1 % in 16/50 (2-way) and 16/50 (4-way) cases, worse by >1 % in 6 and 8. Best gains: −24.7 % (2-way) and −38.7 % (4-way) stall cycles.
* Versus the **best fixed policy** (an oracle that picks per workload): within 1 % in 26/50 and 23/50 cases; more than 5 % worse in 15 and 22 cases; worst gap +15.1 % (2-way) and **+129.4 % (4-way `conflict`)**.
* **Where Adaptive loses to LRU (all 14 cases are `loop`, `fir` or `image`)** — workloads where LRU is already best. Magnitude up to +8.9 %. Likely cause (consistent with the design, not separately proven): leader sets are permanently forced onto the other policies, so exploration has a cost when the current policy is already good.
* **Adaptive never oscillated badly under the default hysteresis:** at most 3 switches per 24 k-request run (mean 0.36).

### 4.1 Why 4-way `conflict` is so bad — a diagnosed limitation
The `conflict` workload touches only sets 0–7, but the PLRU leader sets are at 8 and 24, so the PLRU group collects **0 samples in every window**. The frozen rule requires *all* candidate groups to have `SAMPLE_N` samples before any switch, so the unit **never switched** (verified with the reference model). This is a limitation of the "all groups must be valid" rule combined with static leader placement, not an RTL bug.

Findings (from the tables above):
* **Hysteresis does what it is designed to do on stability.** Total switches over the 6 workloads — 2-way: none **22**, margin-only 13, confirm-only 8, default **3**, strong **1**; 4-way: none **25**, margin-only 21, confirm-only 3, default **1**, strong **0** (`results/figures/ablation_switches.png`). The **consecutive-confirmation counter** is by far the most effective single mechanism; the margin alone helps little.
* **Stability costs responsiveness.** With no hysteresis the 2-way `matmul` run is faster (95 025 vs 102 558 stall cycles) but with 5 switches; the default never switches there. No setting dominates on every workload — hysteresis is a tunable trade-off, not a free improvement.
* **Window size:** smaller windows react faster on the phase-changing workload (2-way `phase`: 1 215 162 at WIN 512/1024 vs 1 290 735 at WIN 4096). In the 4-way cache window size changes little because the starved-group problem of §4.1 dominates.
* Window size is therefore a real design parameter (as the project plan anticipated), but its effect is smaller than that of the leader-set coverage rule.

## 6. Threats to validity
Synthetic and application-*inspired* traces, not processor execution or SPEC; fixed-latency memory (not DRAM); write-through/no-allocate (write cost is large and policy-independent); single run per configuration (all workloads are deterministic, so there is no run-to-run variance, but conclusions are specific to these traces); one set of adaptive defaults except in the ablation; leader-set placement is static.
